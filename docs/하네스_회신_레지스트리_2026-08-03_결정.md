## ① `in_kev` 규칙 정정 — 하네스 코드는 이미 정정된 규칙대로입니다

`gvskb_gate.py`의 `_kev_unchecked_row`는 처음부터 `kev_checked` 필드를 직접 읽습니다
(`cache_sources_used`로 추론한 적이 없습니다). 그래서 `["osv-malicious"]`만 있고
`cisa-kev`는 없는 상태에서도 `kev_checked=false`면 `in_kev=false`를 "악용 없음"이
아니라 "대조 못 함"으로 정확히 처리합니다. 하네스 쪽은 별도 조치가 필요 없습니다 —
계약 문서(`하네스_집행계약.md`) 원문 정정은 그 문서를 갖고 계신 쪽에서 진행해 주세요.

## ② 카탈로그에 버전을 부여할 수 있는가 — **부여하지 않기로 결정**

§3-4 대안을 그대로 채택합니다.

- `denied.packages` → `REJECTED` 즉시 반영 (동의하신 대로, 이름 단위 전 버전 차단은
  보수적이라 안전)
- `approved.*` → **`APPROVED`로 반영하지 않습니다.** 이름 목록("범위")으로만 보관하고,
  실제 버전별 승인은 gvskb가 실제 조회해 `checked_clean`을 낼 때마다 레지스트리가
  자연스럽게 채우도록 둡니다.
- `denied.pending_review` → 반영 안 함(현재 0건)
- `denied.patterns` → 레지스트리 범위 밖(패키지가 아니라 코드/설정 패턴, 게이트 자체 영역)

**버전을 부여하지 않는 이유**: `org-packages.yaml`은 하네스가 "매번 gvskb를 실제로
불러 판정하는" 설계를 전제로 만들어졌습니다(파일 자체 머리말에 "approved 목록에 있다
≠ 안전 확정"이라고 명시). 이 파일에 버전을 얹어 유지보수 대상으로 만들면, 정작 하네스
쪽에서는 아무 이득 없이(어차피 매번 gvskb를 부르므로) 새 버전이 나올 때마다 사람이
갱신해야 하는 카탈로그가 됩니다. 반면 §3-4 대안은 유지보수 비용이 0이고, 레지스트리의
"이 버전이 안전하다"는 판정 의미도 흐리지 않습니다. 말씀하신 §3-6 판단 기준대로 "이
경우 문제 없다"는 쪽을 택했습니다.

**함의**: 초기 승인 목록이 체커 결과가 쌓일 때까지 비어 있는 것을 감수합니다 —
`org-environment.yaml`의 시작 모드를 MONITOR로 둔 이유(§4-1)와 정확히 같은 판단입니다.

## ③ `restricted` 4건의 조건 — 레지스트리 conditions 필드로 옮길 대상이 아닙니다

`requests`·`httpx`·`beautifulsoup4`·`axios`는 전부 외부 HTTP 호출 라이브러리입니다.
"조건"은 `--ignore-scripts`류의 설치 시점 플래그가 아니라, **실제 호출 대상이 승인된
곳인지 코드 리뷰가 필요하다**는 뜻입니다. 이미 `deploy-context.yaml`(행정망 외부통신
금지)과 `closed-network.md`가 정책을 갖고 있고, gvskb의 `scan_code`/`scan_path`가
코드에서 실제 외부 호출을 탐지해(`external_surface`·`GOV-INTERNAL-NET-001`) 게이트에서
잡습니다. 패키지 설치 시점이 아니라 코드 작성 시점의 문제라 레지스트리 conditions로
옮기지 않는 게 맞다고 판단했습니다. `org-packages.yaml`에 이 설명을 주석으로 남겨뒀습니다.
