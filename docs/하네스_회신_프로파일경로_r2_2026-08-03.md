## 3. 참고 제보 — CLI 경로에서 `profile_fallback`이 항상 `null`로 남습니다

저희 작업엔 영향 없는 정보성 제보입니다. 검증 과정에서 발견했습니다.

**재현**: 존재하지 않는 프로필로 `gvskb.cli scan`을 돌리면 stderr에 경고가 뜨고
`public-default-strict`로 정직하게 대체되는데(의도대로 동작), 그 결과 JSON의
`profile_fallback`은 `null`입니다. `profile`도 이미 `public-default-strict`로 바뀌어 있어
겉보기엔 "정상 적용됨"과 구분이 안 됩니다.

**추정 원인**(코드만 읽고 추정, 확정 아님): `scanner.py`의 `_profile_resolution`이 `profile_fallback`을
채우는 지점인데, CLI 쪽에 그보다 먼저 개입하는 예전부터 있던 별도의 "경고 후 기본값 대체" 로직이
있어서, 그 로직이 이름을 미리 유효한 값(`public-default-strict`)으로 바꿔버립니다. `_profile_resolution`
입장에서는 이미 존재하는 정상 프로필을 받은 것처럼 보여 `resolved=True`로 판단하고 `profile_fallback`을
채우지 않는 것으로 보입니다. 즉 CLI의 자체 대체 로직과 신설된 `profile_fallback` 필드가 서로 다른
지점에서 같은 문제를 다르게 처리하고 있어, CLI에서는 새 필드가 무력화되는 모양입니다.

**왜 우리에게 급하지 않은가**: 하네스가 실제로 보는 경로는 MCP(`scan_path`/`scan_code`)이고, 그
경로는 이 CLI 전용 사전 개입을 안 거치는 것으로 코드상 보입니다. 다만 이번 세션에 이미 연결돼
있던 MCP 서버가 최신 코드 반영 전에 뜬 프로세스라, MCP 경로에서 실제로 `profile_fallback`이
정상 채워지는지는 재기동 후 재확인이 필요한 상태입니다 — 저희 쪽 후속 확인 과제로 남겨둡니다.
체커 쪽에서 필요하다고 판단하시면 CLI 쪽도 정리해 주시면 좋겠지만, 급한 결함은 아니라고 봅니다.
