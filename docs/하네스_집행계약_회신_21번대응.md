## 요약

21번에서 요청한 확인 3건·제안 2건에 회신합니다. 코드 반영까지 마쳤습니다.

## ① `org-packages.yaml` 형태 확인 — 혼재형입니다

허용목록(`approved.python`/`npm_frontend`/`npm_backend`)과 차단목록(`denied.packages`)이
공존합니다. 추가로 **이분법에 없던 세 번째 상태** `denied.pending_review`가 있습니다 —
승인도 차단도 아닌 검토중 상태이니, 초기 데이터 반영 시 이 항목들은 **APPROVED/REJECTED
어느 쪽으로도 넣지 말아 주세요**(레지스트리에 대응 상태가 있으면 UNDER_REVIEW로).

반영 방식 제안:
- `approved.*` 항목 → `APPROVED`(`approval_basis=BASELINE_BULK`)
- `denied.packages` 항목 → `REJECTED`
- `denied.pending_review` 항목 → 반영 보류(UNDER_REVIEW 있으면 그쪽으로)

파일 경로: `.claude/references/org-packages.yaml`(이 저장소 안에 있습니다 — 필요하시면
내용을 그대로 전달드리겠습니다).

## ② 캐시 유효기한("1시간") 우려 — 하네스 쪽엔 해당 없음

저희 `gvskb_gate.py`는 **자체 캐시가 전혀 없습니다** — 호출마다 매번 gvskb를 새로 부릅니다.
말씀하신 1시간 TTL은 gvskb 내부 `registry_client.py`의 APPROVED 캐시(3600초)로 보이는데,
그건 이미 소스로 직접 확인했듯 REJECTED(7일)와 비대칭으로 설계되어 있고 — REJECTED는
만료돼도 지우지 않고 `stale=true`로 계속 차단을 유지합니다. 제안하신 "느슨해지는
방향은 재호출 성공 요구, 엄격해지는 방향은 요구 안 함" 규칙과 실제 동작이 이미
일치한다고 확인했습니다. 별도 조치 필요 없습니다.

## ③ `truncated_count` 배치 단위 전달 — 로컬 처리만 하기로 결정

지금처럼 하네스 로컬(`gvskb_gate.py verify-manifest`)에서만 판단하고 ENFORCE 모드에서
차단하는 것으로 유지합니다. 체커 쪽에 배치 메타데이터 전달 기능을 추가로 요청하지
않습니다 — 이미 로컬에서 차단하고 있어 실질적 위험이 없고, 레지스트리·체커 양쪽
스키마 변경 비용 대비 이득이 낮다고 판단했습니다. 필요성이 커지면 다시 요청드리겠습니다.

## ④ ENFORCE 전환 기준 — 확정

말씀하신 구조(직접 의존성만 분모, 비율+건수 이중 기준)를 그대로 채택하되, 저희는
**보수적인 값**으로 확정했습니다:

- 직접 의존성 unknown 비율 **10% 이하** 그리고
- 상시 사용 패키지 **200건 이상** 레지스트리 등록 완료
- 두 조건 **모두** 충족해야 전환 검토(자동 전환 아님 — 수동 판단 참고치)

`org-environment.yaml`의 `enforcement.escalation_guideline`에 반영했습니다.

## ⑤ 차단 우회(예외) 메커니즘 — 사전 승인 코드 방식 도입

말씀하신 원칙 그대로 구현했습니다:

- 자유문장 사유 금지, **사전 승인 코드만** 허용(`org-environment.yaml enforcement.exception_codes`)
- 초기 코드 3종: `SECURITY_PATCH_URGENT`(보안패치 긴급) · `VENDOR_CONFIRMED_FALSE_POSITIVE`(벤더 오탐 확인) · `TEAM_LEAD_APPROVED_TEMP`(팀장 승인 임시)
- **절대차단 4종(malicious·registry_rejected·not_found·in_kev)과 카탈로그 denied/pending_review는 이 코드로도 우회 불가** — 코드로 확인 완료
- 우회 시 `GVSKB_AUDIT_DIR`가 설정돼 있으면 월별 파일(`gate-exceptions-YYYYMM.jsonl`)에 개인식별자 없이 기록되어 집계·월간 보고가 가능합니다
- 실제 동작 검증: 카탈로그 차단·절대차단은 코드가 있어도 그대로 차단됨, 모드표 기반 차단(예: 타이포스쿼트 경고가 ENFORCE에서 차단으로 격상된 경우)은 유효한 코드가 있으면 경고로 낮아지며 이력이 남는 것까지 확인했습니다.

## ⑥ 타이포스쿼트 — 이미 일치, 추가 조치 없음

저희 `gvskb_gate.py`는 원래부터 타이포스쿼트를 절대차단 세트에 넣지 않고 모드표
(MONITOR/WARN=경고, ENFORCE=차단)로만 다루고 있었습니다 — `하네스_집행계약.md` §4-2가
서술한 것과 정확히 같은 구현이라, 이번 철회 확인에 맞춰 따로 고칠 코드는 없었습니다.
