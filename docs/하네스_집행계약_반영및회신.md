# 하네스 집행계약 반영 및 회신

> **성격**: 레지스트리팀이 보낸 두 문서(`하네스_집행계약.md`, `하네스-집행계약_협의요청_레지스트리 서비스_2026-08-02.md`)에
> 대한 하네스팀(vibe_harness_claude)의 반영 내용 + 6개 결정사항 회신.
> 원본 두 문서는 이 저장소 밖(전달받은 원본)이 정본이며, 이 문서는 하네스 코드에
> 반영한 실제 구현과 그 근거를 남기는 실행 기록이다.
> **작성일**: 2026-08-02

## 0. 핵심 요지

gvskb는 판정(verdict)만 내리고, gg-trusted-registry는 그 판정을 저장할 뿐이다.
**실제로 pip/npm install을 실행하는 것은 하네스뿐**이므로, 이 계약의 무게중심은
"하네스가 그 판정을 실제로 집행하는가"에 있다. 이번 반영에서 그 집행 지점을
`.claude/enforcement/gvskb_gate.py`(Python, 판정엔진 겸 CLI)와
`.claude/enforcement/gvskb_gate.js`(Node, 얇은 래퍼) 두 파일로 만들었다.
판정 로직은 Python 한 곳에만 있다 — 같은 보안 판단을 두 언어로 각각 구현하면
반드시 드리프트가 생기기 때문에, JS는 Python 프로세스를 호출해 그 결과(종료 코드)를
그대로 따르기만 한다.

## 1. 6개 결정사항 회신

### 결정 ① verdict → 조치 매핑

`하네스_집행계약.md` §3·§4의 표를 그대로 채택해 `gvskb_gate.py`의 `_verdict_row`/
`_typosquat_row`/`_absolute_block`으로 코드화했다. 절대차단(모드 무관):
`malicious`·`registry_rejected`·`not_found`·`in_kev=true`. 나머지는 MONITOR/WARN/
ENFORCE 3단 표를 그대로 따른다.

### 결정 ② env_grade는 개발자가 고르지 않는다 — **가장 시급하다고 판단, 우선 반영**

협의요청 §5-2(a)를 채택했다. `gvskb_gate.py`가 컨텍스트로 자동 결정한다:

- 기본값 **E1**(개인 PC 세션)
- `CI`·`GITHUB_ACTIONS`·`GITLAB_CI`·`JENKINS_URL`·`BUILDKITE` 환경변수가 보이면 **E2**로 자동 상향
- 하향(E2→E1/E0)은 `GVSKB_GATE_ENV_GRADE` 환경변수로 **명시적**으로만 가능 — 기본 경로에는 없다

E0은 자동으로 내려가지 않는다(협의요청이 우려한 "귀찮으면 항상 가장 느슨한 값을 고른다"는
도덕적 해이를 기본 경로에서 원천 차단). 다만 "하향 시 사전기록"까지는 이번 반영에
포함하지 않았다 — 환경변수 override 자체가 감사로그에 `caller=harness:auto`로 남는 것
이상의 별도 승인 워크플로는 아직 없다. 필요하면 다음 단계에서 추가할 수 있다.

### 결정 ③ unknown 단계적 전환 기준

시작 모드는 **MONITOR**로 확정했다(협의요청 §11: 레지스트리 데이터가 아직 데모 수준).
`org-environment.yaml`의 `enforcement.escalation_guideline`에 전환 검토용 참고 수치
(unknown 비율 30%↓→WARN 검토, 10%↓→ENFORCE 검토)를 넣었지만 **자동 전환은 구현하지
않았다** — 실측 데이터 없이 임계값을 코드로 박아 넣는 게 오히려 위험하다고 판단했다.
사람이 감사로그(`GVSKB_AUDIT_DIR`)를 보고 수동으로 모드를 올리는 방식을 기본으로 한다.

### 결정 ④ 기존 카탈로그(org-packages.yaml) vs gvskb/레지스트리 우선순위

`하네스_집행계약.md` §6-3의 5단계 우선순위를 그대로 채택해 구현했다:

1. 카탈로그 `denied` → 차단 (gvskb를 부르지도 않는다)
2. 카탈로그 `pending_review` → 차단(승인 아님)
3. gvskb 절대차단(`malicious`/`registry_rejected`/`not_found`/`in_kev`) → 차단
4. 나머지는 verdict별 모드표를 그대로 적용(카탈로그 `approved`는 여기서 gvskb 호출을
   생략시키지 않는다 — "카탈로그는 확장이지 대체가 아니다"라는 원칙대로, 승인 목록에
   있어도 항상 gvskb를 실제로 부른다)

차단 두 개(①②)를 항상 허용보다 먼저 평가한다.

### 결정 ⑤ REJECTED 캐시 만료(7일) 처리

gvskb 쪽 `registry_client.py`를 직접 확인한 결과, **이미 올바르게 구현되어 있었다** —
TTL이 지나도 `REJECTED` 캐시를 삭제하지 않고 `stale: true`를 붙여 계속 반환하며,
`apply_registry_decision`은 `stale` 여부와 무관하게 `verdict=registry_rejected`를 유지한다.
하네스 쪽은 이 verdict를 그대로 절대차단 목록에 포함시켰으므로, 레지스트리 연결이
끊긴 상태에서도 차단이 조용히 풀리지 않는다. 하네스 회신: **경고로 낮추지 말라는
계약 §3-2 요구사항은 이미 gvskb 엔진 레벨에서 만족되어 있다.**

### 결정 ⑥ MISMATCH(해시/이름 불일치) 처리

gvskb 최신 소스(`schema.py`/`check_package.py`)를 직접 확인했으나 **아직 MISMATCH를
나타내는 필드가 없다**. 하네스 쪽 결정: `gvskb_gate.py`의 `_absolute_block`에
`result.get("mismatch")`를 방어적으로 확인하는 코드를 미리 넣어 두었다 — gvskb가
이 필드를 추가하는 즉시(코드 변경 없이) 절대차단 세트에 자동 편입된다. **레지스트리팀에
요청**: 필드명을 `mismatch`(bool) 또는 `mismatch_reason`(str)로 맞춰주면 하네스 쪽
추가 작업 없이 바로 반영된다.

## 2. 실제 구현 위치

| 파일 | 역할 |
|---|---|
| `.claude/enforcement/gvskb_gate.py` | 판정엔진 + CLI(`check`/`install`/`verify-manifest`). gvskb를 직접 import해 호출하고 `gvskb.audit.record_package_check`로 감사로그(`caller=harness:auto`)를 남긴다 |
| `.claude/enforcement/gvskb_gate.js` | Node 래퍼(`check`/`install`) — Python 프로세스를 spawn해 결과만 따른다 |
| `references/org-environment.yaml` `enforcement` 블록 | 모드 기본값(MONITOR)·전환 참고치·env_grade 자동화 여부 |
| `references/org-packages.yaml` `automation` 블록 | 하네스 로컬 카탈로그(gg-trusted-registry와 별개)의 실제 집행 방식 명시 |
| `CLAUDE.md`/`solution-architect.md`/`security-reviewer.md` | 새 패키지는 `gvskb_gate` 경유 의무화, L3/🔴 배포 게이트는 `verify-manifest --mode ENFORCE` 필수 |

## 3. 하네스팀이 참고만 하고 반영하지 않은 것 (레지스트리팀 몫)

- registry-mcp 자체 연동 — `09-mcp-ecosystem-architecture.md`가 그렸던 "하네스가
  registry-mcp를 먼저 조회"하는 구조는 **폐기되었다**(협의요청 §2 확인). 하네스는
  gvskb 하나만 부르고, gg-trusted-registry 조회는 gvskb가 내부에서
  (`GVSKB_REGISTRY_URL`) 처리한다. 이 문서를 반영하면서 지난번 하네스 쪽에서
  잘못 설계했던 "외부 플랫폼이 org-packages.yaml을 직접 갱신한다"는 가정도
  함께 폐기했다(§1 결정 ④에서 정정).
- E3(대민·개인정보) 등급 — 애초에 바이브코딩 대상이 아니므로 gvskb·하네스 모두
  파라미터로 받지 않는다. 하네스 쪽 존/성숙도 체계(`deploy-context.yaml`
  external+`data-traffic-light.yaml` red)와 사실상 대응되므로 별도 매핑을
  추가하지 않았다.
